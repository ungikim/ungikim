최근 개인 인프라를 Cloudflare로 옮겼다.

서버와 데이터베이스, 백그라운드 프로세스를 직접 관리하는 대신 여러 관리형 서비스를 조합해서 사용하고 있다. 애플리케이션 코드와 인프라 설정, 공통 라이브러리, 개발 환경은 ungikim-ops라는 하나의 Git 저장소에서 관리한다.

이 과정에서 AI 코딩 에이전트가 큰 역할을 했다.

이전에는 기술적으로 불가능했던 일을 하게 된 것은 아니다. 달라진 것은 아이디어를 실제로 사용할 수 있는 형태로 구현하는 데 필요한 노력이다. 덕분에 개인 인프라를 구성하고 운영하는 일이 다시 재미있어졌다.

하나의 저장소에서 관리하기

ungikim-ops는 개인적으로 사용하는 애플리케이션과 인프라, 개발 환경을 관리하는 모노레포(monorepo)다.

현재 저장소는 대략 다음과 같은 구조로 되어 있다.

ungikim-ops/
 ├─ apps/       애플리케이션
 ├─ workers/    API 및 이벤트 기반 서비스
 ├─ packages/   공통 라이브러리와 설정
 ├─ data/       선언적 데이터와 스키마
 ├─ infra/
 │   ├─ terraform/
 │   ├─ ansible/
 │   └─ dotfiles/
 ├─ tools/      개발 및 검증 도구
 ├─ docs/       설계 및 운영 문서
 └─ .github/    CI/CD와 자동화

pnpm workspace와 Turborepo를 사용하고, 개별 애플리케이션은 필요에 따라 Astro, Next.js, Vite를 사용한다.

모든 애플리케이션이 동일한 프레임워크를 사용할 필요는 없다. 중요한 것은 일관된 방식으로 개발하고 빌드하고 배포할 수 있는 환경이다.

모든 것을 하나의 저장소에서 관리하는 방식은 AI 코딩 에이전트를 사용할 때도 효과적이다.

새로운 애플리케이션을 추가할 때 에이전트는 기존 애플리케이션과 인프라 설정, 공통 패키지, 배포 워크플로를 함께 참고할 수 있다. 매번 전체 구조와 구성 요소 사이의 관계를 설명할 필요가 없다.

인프라 역시 AI 에이전트와 함께 작업할 수 있는 코드베이스의 일부가 됐다.

Cloudflare로 옮기기

개인적으로 사용하는 서비스 대부분은 높은 컴퓨팅 성능을 요구하거나 많은 요청을 처리하지 않는다.

이런 서비스를 실행하기 위해 서버를 직접 유지하는 대신 Cloudflare의 관리형 서비스를 중심으로 인프라를 구성했다.

Cloudflare
 ├─ Pages       웹 애플리케이션
 ├─ Workers     API 및 이벤트 처리
 ├─ DNS         도메인 관리
 ├─ Access      인증 및 접근 제어
 ├─ R2          Terraform state 저장
 ├─ Workers AI  LLM 및 임베딩
 ├─ Vectorize   벡터 저장 및 검색
 └─ Queues      비동기 작업 처리

웹 애플리케이션은 Cloudflare Pages에 배포하고, 동적인 요청과 백그라운드 작업은 Workers에서 처리한다. 개인 블로그인 ungikim.me는 기존 GitHub Pages 배포 방식을 유지하고 있다.

지난 글에서 소개한 Mem0 OSS도 Cloudflare Workers에서 실행한다. 모델 추론과 임베딩은 Workers AI를 사용하고, 기억은 Vectorize에 저장하며, 비동기 기억 처리는 Queues에 맡긴다.

새로운 서비스를 만들 때마다 서버를 준비하거나 데이터베이스를 설치하고 메시지 브로커를 운영할 필요가 없다.

사용량이 많지 않은 개인 프로젝트에서는 Cloudflare의 무료 할당량을 활용해 큰 고정 비용 없이 시작할 수도 있다.

소프트웨어가 실행되는 환경을 관리하는 데 사용하는 시간은 줄어들고, 소프트웨어 자체를 만드는 데 사용할 수 있는 시간은 늘어났다.

인프라를 데이터로 정의하기

Cloudflare Pages에 배포하는 사이트는 data/cloudflare-pages-sites.json이라는 하나의 JSON 파일에서 정의한다.

각 항목에는 애플리케이션의 workspace, 소스 디렉터리, 빌드 결과물, 배포 브랜치, 커스텀 도메인, 배포 환경 등의 정보를 담는다.

Terraform과 GitHub Actions는 같은 레지스트리를 참조한다.

cloudflare-pages-sites.json
       │
       ├─ Terraform
       │    ├─ Pages 프로젝트
       │    ├─ 커스텀 도메인
       │    ├─ DNS 레코드
       │    └─ Redirect 규칙
       │
       └─ GitHub Actions
            ├─ 배포 대상 선택
            ├─ 애플리케이션 빌드
            └─ Cloudflare Pages 배포

애플리케이션마다 Terraform 리소스와 GitHub Actions 워크플로를 새로 작성하는 대신, 레지스트리에 항목을 추가해 기존 인프라를 재사용한다.

현재 청첩장, 포트폴리오 웹사이트, PMS 프로토타입을 이 방식으로 관리하고 있다.

Terraform state도 Cloudflare R2의 S3 호환 API를 통해 저장한다.

이 구조에서 특히 마음에 드는 점은 AI 코딩 에이전트와 잘 맞는다는 것이다. 새로운 애플리케이션을 추가하는 일이 기존 규칙을 따르는 비교적 명확한 작업이 된다.

애플리케이션을 작성하는 것과 인터넷에서 실제로 사용할 수 있는 상태로 만드는 것 사이의 거리가 짧아졌다.

배포 자동화하기

애플리케이션 빌드와 인프라 프로비저닝, Pages 배포는 GitHub Actions가 담당한다.

애플리케이션 코드가 변경되면 관련된 사이트를 빌드하고 배포한다. 인프라 설정이나 레지스트리가 변경되면 데이터를 검증하고 Terraform을 적용한 뒤 등록된 사이트를 배포한다.

애플리케이션 변경
 → Git push
 → 변경된 사이트 선택
 → Build
 → Cloudflare Pages

인프라 변경
 → Git push
 → 데이터 검증
 → Terraform plan
 → Terraform apply
 → 등록된 사이트 배포

배포 워크플로에서는 배포 직전에 빌드가 여전히 최신 상태인지도 확인한다. 이전 빌드가 새로운 배포를 덮어쓰는 상황을 방지하기 위해서다.

애플리케이션 배포에 사용하는 인증 정보와 인프라 프로비저닝에 사용하는 인증 정보도 분리했다.

물론 이런 방식 자체가 새로운 것은 아니다. Infrastructure as Code와 CI/CD는 AI 코딩 에이전트가 등장하기 훨씬 전부터 존재했다.

AI로 인해 달라진 것은 개인 프로젝트에서 이런 구성 요소들을 연결하기 위해 투자해야 하는 노력이다.

자동화는 한 번 구성해 두면 이후에 추가하는 모든 애플리케이션에 활용할 수 있다. 같은 배포 문제를 반복해서 해결할 필요가 없다.

나에게 필요한 소프트웨어 만들기

AI는 작은 소프트웨어로 해결할 수 있는 문제에 접근하는 방식도 바꿔 놓았다.

기존 서비스를 찾아 사용하고 그 서비스에 맞춰 내 작업 방식을 변경하는 대신, 나에게 맞는 소프트웨어를 직접 만드는 것이 현실적인 선택지가 됐다.

저장소에는 웹사이트뿐 아니라 작은 macOS 애플리케이션, 개발 도구, 그리고 개인 운영체제의 일부로 사용할 API도 포함되어 있다.

API의 기억 레이어가 대표적인 사례다.

호스팅된 기억 서비스를 사용하는 대신 Mem0 OSS를 Cloudflare Workers에서 실행할 수 있도록 수정하고 Cloudflare의 관리형 서비스와 연결했다.

AI Agent
 → MCP
 → Personal API
 → Mem0 OSS
      ├─ Workers AI
      ├─ Vectorize
      └─ Queues

이런 애플리케이션이 반드시 하나의 제품이 될 필요는 없다. 모든 사용 사례를 지원하거나 복잡한 사용자 인터페이스를 제공할 필요도 없다.

나에게 필요한 기능을 제공하면 된다.

이미 구성된 배포 환경은 이런 접근 방식을 더욱 매력적으로 만든다. 작은 애플리케이션을 만드는 것뿐 아니라 실제로 사용할 수 있는 곳에 배포하는 것도 쉬워졌다.

AI 에이전트를 위한 인프라

개발 환경 자체도 관리하는 인프라의 일부가 됐다.

현재 주로 사용하는 코딩 에이전트는 Pi다. 저장소에 특화된 지침은 AGENTS.md에 정의하고, 여러 프로젝트에서 재사용하는 에이전트 지침과 Skills는 dotfiles와 함께 관리한다.

infra/dotfiles/pi/
 ├─ AGENTS.md
 ├─ skills/
 └─ external-skills.tsv

프로젝트 컨텍스트와 개인 컨텍스트도 구분해서 관리한다.

프로젝트의 아키텍처와 기술적인 결정, 지속적으로 적용할 개발 규칙은 Git 저장소에 남긴다. 개인적인 선호와 일반적인 업무 맥락은 Mem0에 저장하고 에이전트가 MCP를 통해 접근할 수 있도록 한다.

AI Agent
 ├─ Git Repository
 │   ├─ 프로젝트 컨텍스트
 │   ├─ 개발 규칙
 │   └─ Skills
 │
 └─ Mem0 MCP
      ├─ 개인적인 선호
      ├─ 개인 컨텍스트
      └─ 일반적인 업무 맥락

프로젝트에 관한 정보의 기준은 Git 저장소다. 기억은 문서화된 결정을 대체하는 것이 아니라 보완하는 역할을 한다.

사용하는 모델이나 코딩 에이전트가 바뀌더라도 지금 구성한 환경을 계속 활용할 수 있기를 바란다.

AI 에이전트가 무엇을 만들 수 있는지뿐 아니라 에이전트가 작업하는 환경을 어떻게 구성할 것인지에도 관심이 생겼다.

줄어든 운영 부담, 여전한 책임

물론 소프트웨어를 만드는 일이 쉬워졌다고 해서 유지보수 비용까지 사라지는 것은 아니다.

AI가 작성한 코드에도 버그와 보안 문제, 불필요한 복잡성이 존재할 수 있다. AI 에이전트가 인프라를 변경했다고 해서 변경 사항을 이해해야 할 책임까지 없어지는 것은 아니다.

Cloudflare로 인프라를 이전하면서 또 다른 의존성도 생겼다. Workers, Vectorize, Queues를 중심으로 구성한 애플리케이션을 다른 플랫폼으로 옮기려면 코드 수정이 필요할 수 있다.

하지만 개인 프로젝트에서 모든 구성 요소를 직접 운영하거나 이식성을 최대한 확보하는 것이 항상 중요한 것은 아니다.

내가 실제로 만들고 싶은 것에 더 많은 시간을 사용할 수 있다면 인프라 운영을 플랫폼에 위임하는 것도 괜찮다고 생각한다.

오히려 무엇을 만들 가치가 있는지 판단하는 일이 더 중요해졌다.

다시 재미있어진 인프라

Cloudflare는 직접 관리해야 하는 인프라를 줄여주었고, AI는 소프트웨어를 구현하는 데 필요한 노력을 줄여주었다. 모노레포와 자동화된 배포 환경은 이 둘을 연결한다.

아이디어
 → AI 코딩 에이전트
 → 코드와 인프라 설정
 → Git
 → Build & Deploy
 → 실제로 사용하는 소프트웨어

각각의 기술 자체는 특별히 새로운 것이 아니다.

내가 재미를 느끼는 부분은 이 기술들을 조합하는 과정이다.

메모에 남거나 미완성 실험으로 끝났을 작은 아이디어를 이제는 주말 내내 환경을 구성하고 문제를 해결하지 않아도 실제로 동작하는 애플리케이션으로 만들 수 있다.

AI가 내가 개인 프로젝트를 좋아하는 이유를 근본적으로 바꾼 것은 아니다. 여전히 새로운 기술을 배우고, 나에게 필요한 도구를 만들고, 매일 사용하는 환경을 개선하는 과정이 좋다.

달라진 것은 아이디어를 떠올리고 그것을 실현하기까지의 번거로움이 줄어들었다는 점이다.

덕분에 인프라를 운영하는 일이 다시 재미있어졌다.
